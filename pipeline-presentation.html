Section 1 — Chronological File Creation

Pipeline in Order of File Creation Date

Each stage builds on the previous one. Dates are from ls -lt. The core grouping happened in November, enrichment in January–February.

1
13 Nov
🔍 Fetch all products from Search API fetch_products_with_attributes.js

Calls the Product Search Service to get all product listings, then for each product individually calls the Product API (to get isVap) and the Attributes API (to get raw spec groups). Uses a checkpoint file every 50 products so it can resume if interrupted. 100ms delay between calls, exponential backoff on errors.

Exact API calls

  • Search: GET /product-search-service/search?channelId=557576&catalogueType=PUBLIC&pageSize=2000
  • Product detail: GET /product-api/products/{productCode} → extracts isVap (boolean)
  • Attributes: GET /product-api/{productCode}/2357124/attributes → extracts sourceAttributes (groups array with Specifications)

Output: products_with_attributes.json (root) + checkpoint file

  • Each product enriched with isVap: true/false
  • Each product enriched with sourceAttributes: { groups: [{ name: "Specifications", attributes: [...] }] }
  • _metadata block with fetch stats and source URLs
branchId: 2357124 delay: 100ms Checkpoint every 50 products Output: products_with_attributes.json

18 Nov
🎯 Final grouping algorithm — v6 (reads v5, re-groups) create-v6.cjs

The definitive grouping step. Reads products-grouped-by-variant_v5.json, flattens all products per brand, then re-groups by normalizeTitle(). Four bugs were fixed in this version vs earlier ones.

normalizeTitle() — exact removal order

  • 1. Size patterns: /\d+\s*x\s*\d+(…)(mm|cm|m)?/gi — e.g. "1200x900mm", "3.0x1.8m"
  • 2. Individual dims: /\d+\s*(mm|cm|m)\d?/gi — "630mm", "10m2", "5m3"
  • 3. Parenthetical area: /\(?\d+m[23]\)?/gi — "(10M2)", "(5m3)"
  • 4. Whitespace normalise to single spaces before material matching (bug fix)
  • 5. Word variations: "underfloor" ↔ "under floor" normalised
  • 6. Directional: "left hand", "right hand", "left", "right"
  • 7. Colour combos: /\b\w+\s*\/\s*\w+\b/gi — "Grey/Chrome"
  • 8. Materials list (sorted longest-first): complex finishes first (e.g. "brushed platinum gold"), then standard finishes (brushed, polished, matte…), glass types, wood types, base colours, temperatures

4 bugs fixed in v6 vs v5

  • Whitespace bug: "Polished Stainless   Steel" (extra spaces) failed multi-word match → fix: normalise whitespace first
  • m2/m3 notation: "(10M2)" size not stripped → Stiebel Eltron heating packs not grouped
  • underfloor vs under floor: different spacing = different groups → normalise
  • Missing colour names: Fume, Green, Tangerine Orange not in list → LAUFEN Kartell racks not grouped
Input: v5 JSON ~60 tokens in materials array, sorted by length DESC Output: products-grouped-by-variant_v6.json

27 Nov
⭐ Create products_with_variants3.json — THE MAIN FILE create-variants3.cjs

This is the core script. It merges v6 grouping with products_with_attributes.json to produce the definitive file. It introduces intelligent dimension matching, improved findCommonTitle(), and full sourceAttributes embedding.

Step-by-step logic inside create-variants3.cjs

1
Load inputs: Read products-grouped-by-variant_v6.json + products_with_attributes.json. Build a Map(productCode → attributes) for O(1) lookup.
2
For each brand's groups (skip groups with ≤ 1 product): Call findCommonTitle(titles[]) — strips sizes, directions, temperatures, and 15 material/colour terms from each title, then finds the longest common consecutive word sequence across all titles in the group. Falls back to common prefix words if no sequence found. Capitalises result, handles Roman numerals and "AXA" brand.
3
Generate family ID: fam_ + MD5(brand.toLowerCase() + "-" + commonTitle.toLowerCase())[0..12]
4
For each product in the group, build a variant object: Look up sourceAttributes from the map, filter to only the "Specifications" group (dropping marketing/other groups), then call extractVariantAttributes(productTitle, commonTitle, filteredAttributes).
5
extractVariantAttributes() — builds the attributes object:
• sizes: regex for "NxNmm" multi-dim patterns → array
• Individual dims: if no sizes, match "Nmm" tokens → call matchDimensionToSpec() to map each to the correct spec name (Width/Height/Depth/etc) using ±50mm tolerance
• coverage: area patterns "(10M2)"
• orientation: "Left Hand Bowl" takes priority for vanities, else "Left Hand" / "Right Hand" / "Left" / "Right"
• temperature: "Cold" / "Warm" / "Hot"
• uniqueDescriptors / color: words remaining after removing common title words, excluding a hardcoded exclude list (hand, rail, basin, tap, mixer, shower, etc.)
6
matchDimensionToSpec() — spec name lookup: Parses the numeric value from "Nmm", searches sourceAttributes.groups[0].attributes for specs where |specValue - numericValue| ≤ 50. Excluded from matching: Recommended Pressure Range, Temperature, Flow Rate, Capacity, Weight, Star Rating, WELS Rating. When multiple specs match, picks highest priority: Benchtop Thickness → Width → Height → Depth → Length → Diameter → Min/Max Width/Height → Projection → Reach → Arm Length → Shower Head Width → Fixing Point Distance. If Min and Max have the same value (±50mm), collapses to base name (e.g. "Width" instead of "Minimum Width").
7
extractVariantOptions() — builds variantOptions at family level: Collects all values for each attribute key across all variants. If multiple different dimension-type keys exist across variants (e.g. some have "Width", others have "Height"), consolidates them all into a single "dimension" key. Only includes keys where there are ≥ 2 unique values. Renames "sizes" → "size", "dimensions" → "dimension".
8
Merge duplicate families: After all groups are processed, merge any families with identical brand:productFamilyTitle key by combining their variants and re-running extractVariantOptions().
9
Write output: public/products_with_variants3.json with _metadata block (version: 3, statistics, variantTypes array) and families array.
Input: v6 grouping JSON Input: products_with_attributes.json Only groups with ≥ 2 products become families Output: products_with_variants3.json (base)

20 Jan
💲 Enrich — Live Pricing fetch_prices.cjs

Reads products_with_variants3.json, extracts all product codes, and calls Reece's pricing endpoint in batches of 50 with a 500ms delay between batches.

Exact API call

  • URL: POST https://www.reece.com.au/trsonline/products/prices/batch
  • Body: { postCode: "2018", products: [{ productCode, packs: ["PACK1"] }] }
  • Response path: response.prices[].cmp.PACK1.gstInclusive → stored as variant.price
  • Variants without a price get variant.price = null
Batch: 50 products Delay: 500ms between batches Postcode: 2018 (Sydney) Adds: variant.price (GST incl., AUD) Writes back to: products_with_variants3.json

🖼️ Enrich — Digital Assets (3D + Images) fetch_assets.cjs

Batch-fetches all 5 asset types per product from the internal Digital Asset Service. 300ms delay between batches of 50.

Exact API call

  • URL: POST http://reeceausys.reece.com.au/digital-asset-service/products/assets/batch
  • Body: { productNumbers: [int, …], subAssetType: ["GLB_3D_Planner", "GLB_3D_Planner_Void", "GLB_3D_Planner_Review", "Hero", "Supporting_Image"] }
  • Note: productCode is cast to parseInt() before sending
  • Response: array of asset objects grouped by asset.productNumber
  • Stored as: variant.assets = [{ productNumber, subAssetType, title, thumbnails: [{width, height, absoluteUrl}] }]

📸 Extract productImages from assets (1200×900 only) scripts/add-product-images.js

Pure local transformation — no API call. Reads the already-embedded assets array and pulls out only 1200×900 thumbnail URLs.

Exact logic

  • Filter variant.assets to subAssetType === "Hero" || "Supporting_Image"
  • Sort Hero first, Supporting_Image second
  • For each, find thumbnails.find(t => t.width === 1200 && t.height === 900)
  • Push thumbnail.absoluteUrl to variant.productImages
No API — local transform only Adds: variant.productImages [] (flat URL array) Result: 23,140 images, avg 2.74 per variant

🗂️ Enrich — Category Descriptions fetch_category_description.cjs

Re-hits the Product API for each variant to retrieve categoryDescription. Processes in parallel batches of 10, with checkpointing every 100 products and exponential retry (up to 3 attempts).

Exact API call

  • URL: GET http://trsausys.reecenet.org/product-api/products/{productCode}
  • Extracts: productData.categoryDescription
  • Batch: 10 parallel fetches at a time, 100ms delay between batches
  • Checkpoint: saved every 100 products to category_description_checkpoint.json, deleted on completion
  • Retry: 3 attempts with RETRY_DELAY × attempt backoff (1s, 2s)
  • Stored as: variant.categoryDescription (e.g. "Shower Bases", "Tapware", "Vanities"…)

Section 4 — isVap

What is isVap and how is it fetched?

isVap (Visualizer Applicable Product) determines whether a product can be shown in the 3D bathroom planner.

How it's fetched

1
GET /product-api/products/{productCode}
2
Extract: productData.isVap — a boolean on the product API response
3
Store: product.isVap = productData.isVap (defaults to false if API fails)
4
Later: The v6 grouping and family creation scripts carry this field into the variant's source data, so the UI can filter to only show VAP-eligible products in the planner.

What isVap controls

  • isVap = true: Product has 3D GLB assets and can be placed in the bathroom planner
  • isVap = false: Product is catalogued but not available in the planner
  • Counted in _metadata.vapProducts stats at fetch time
  • 3D asset types (GLB_3D_Planner, GLB_3D_Planner_Void, GLB_3D_Planner_Review) only meaningful for VAP products
